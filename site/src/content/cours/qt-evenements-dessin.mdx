## Introduction

Les signaux/slots suffisent tant qu'on **assemble** des widgets existants ; pour en **créer** — redéfinir un comportement au clavier, dessiner soi-même — il faut descendre d'un étage : les **évènements**. Ce module ferme la série en descendant sous le capot, puis en ouvrant deux portes latérales (fichiers, QML). Objectifs :

- comprendre le trajet d'un évènement, redéfinir les *handlers*, filtrer ;
- dessiner un widget avec **QPainter** ;
- manipuler fichiers et flux — Qt sans fenêtre ;
- savoir ce qu'est **Qt Quick/QML**, et quand y penser.

## Le trajet d'un évènement

Quand vous pressez une touche, le système la transmet à `QApplication`, qui fabrique un objet **`QEvent`** (ici un `QKeyEvent`) et l'achemine au widget destinataire par sa méthode **`event()`**. Celle-ci n'y touche pas : elle **aiguille** vers le *handler* spécialisé — `keyPressEvent()`, `mousePressEvent()`, `resizeEvent()`, `paintEvent()`… Chaque évènement transporte ses informations (`QResizeEvent::size()` et `oldSize()`, par exemple) ; certains viennent du système (souris, clavier), d'autres d'ailleurs (`QTimerEvent`).

Redéfinir un comportement = **surcharger le handler** correspondant. Et le cas d'école où le handler ne suffit pas : la touche **Tab**, consommée par la gestion du focus *avant* d'atteindre `keyPressEvent` — il faut alors redéfinir `event()` lui-même (fichier réel, compilé et exécuté par le harnais) :

Deux règles de savoir-vivre : renvoyer `true` quand l'évènement est traité (il s'arrête là), et **toujours passer le reste à la classe de base** (`QWidget::event(...)`, `QWidget::keyPressEvent(...)`) — casser la chaîne, c'est casser le focus, les raccourcis, la fermeture…

Compléments à connaître :

- **filtrer** : `objet->installEventFilter(filtre)` fait transiter les évènements d'un objet par le `eventFilter()` d'un autre — jusqu'à espionner toute l'application en filtrant `qApp` ; renvoyer `true` stoppe l'évènement ;
- **émettre** : `QCoreApplication::sendEvent()` (immédiat) et `postEvent()` (déposé dans la **file d'évènements**, traité au prochain tour de boucle — ce qui permet à Qt d'optimiser : plusieurs demandes de redessin se **compressent** en une seule) ; ses propres types d'évènements se créent en sous-classant `QEvent` au-delà de `QEvent::User`.

## Dessiner : QPainter

<Duo>
  Tout ce que Qt affiche passe par **QPainter** : primitives (lignes, ellipses, polygones, courbes, texte), transformations (translation, rotation, échelle), découpage. Le repère : (0,0) en **haut à gauche**. La règle absolue : on ne peint que dans **`paintEvent()`**, sur un painter construit sur `this` — et pour redessiner, on n'appelle pas `paintEvent` soi-même : **`update()`** poste une demande dans la file (compression automatique des redessins). QPainter sait aussi peindre ailleurs que sur un widget : une `QImage` (travail hors écran), une imprimante (`QPrinter`)…

## Fichiers et flux : Qt sans fenêtre

Qt vit aussi très bien sans écran. **`QFile`** représente le fichier (existence, ouverture — `QIODevice::ReadOnly`, `WriteOnly`, `Append`… —, suppression) ; les **flux** travaillent dessus : **`QTextStream`** pour le texte (encodages gérés), **`QDataStream`** pour le binaire (et la sérialisation d'objets Qt). La beauté du montage : ces flux acceptent n'importe quel **`QIODevice`** — fichier, tampon mémoire (`QBuffer`), socket réseau (`QTcpSocket`) : le même code lit un fichier local ou une connexion réseau.

## L'autre monde : Qt Quick et QML

Ce cours a suivi la voie **QtWidgets** — celle des applications de bureau classiques. Depuis Qt 5, une seconde voie existe : **Qt Quick**, où l'interface se décrit en **QML**, un langage *déclaratif* (on décrit ce qu'on veut voir, avec du JavaScript pour la petite logique, et du C++ en dessous quand il faut de la puissance) :

```qml
Rectangle {
    width: 220; height: 90; color: "whitesmoke"
    Text { anchors.centerIn: parent; text: "Hello world!"; color: "steelblue" }
}
```

Les deux voies sont vivantes et officielles. Le partage grossier : **Widgets** pour les applications de bureau denses (formulaires, tableaux, outillage professionnel — le *look and feel* natif), **Qt Quick** pour le mobile, l'embarqué, le tactile et les interfaces animées. Ce que vous avez appris ici — QObject, signaux/slots, la boucle d'évènements, l'outillage — porte **les deux** mondes : QML s'appuie sur le même socle.

## Récapitulatif

- Un évènement voyage : système → `QApplication` → `event()` du widget → *handler* spécialisé ; on surcharge le handler (ou `event()` pour Tab), on renvoie `true` si traité, on **passe le reste à la classe de base**.
- Filtres (`installEventFilter`) pour intercepter ; `sendEvent`/`postEvent` pour émettre — la file compresse (plusieurs `update()` → un `paintEvent`).
- **QPainter**, uniquement dans `paintEvent()` ; origine en haut à gauche ; `update()` pour demander un redessin.
- **QFile** + flux (`QTextStream`/`QDataStream`) sur tout `QIODevice` — fichier, tampon ou socket ; `QScrollArea` pour faire défiler.
- **Qt Quick/QML** : la voie déclarative (mobile, embarqué, animé) — même socle, autre peau.
